### Выбор размера рабочей ноды и их количество

Основываясь по материалам по `Best practice`:

- `Большое количество небольших нод` приведет к растут накладных `расходов на обслуживание` каждой ноды;
- При [сильном уплотнении приложений](https://kubernetes.io/docs/concepts/scheduling-eviction/resource-bin-packing/) на `небольшом количестве крупных нод` способствует `к росту рисков на отказ`;
- По вопросу сколько подов можно запустить на ноду:
  - по Факту ограничений нет
  - по предоставляемым облачными провайдерами ресурсов от 110 до 250 подов на ноду
  - По умолчанию в конфигурации агента Kubelet прописано значение [110](https://kubernetes.io/docs/reference/config-api/kubelet-config.v1beta1/#:~:text=Default%3A%20%22promiscuous%2Dbridge%22-,maxPods,-int32) подов на ноду

```
Для данного проекта целесообразно взять распространенный типовой размер рабочей ноды
В соотношении 8 vCPU / 32 ГБ.
```

#### Учёт ресурсов для служб ОС linux на рабочей ноде

> На каждой рабочей ноде часть ресурсов съедают системные службы и компоненты:

- `kube-reserved` + `system-reserved` (kubelet, container runtime(CRI), kube-proxy,
  ядро ОС, sshd и т.д.) - добавляем в расчет ~ **5 % CPU и 5 % RAM**;
- Демонсеты мониторинга и сбора логов (node-exporter, cAdvisor, Fluentd/Filebeat,
  агент СNI и т.п.) - ещё добавочно ~**0,5 ядра и ~1,5 ГБ**;
- Чтобы избежать нехватки ресурсов при **пороге вытеснения (eviction threshold)**, ещё ~**1 ГБ** RAM к нашему проекту на ноду.

Расчёт полезной ёмкости `одной рабочей ноды (8 vCPU / 32 ГБ)`:

| Необходимые Расходы на функционирование ноды | CPU | RAM |
|---|---|---|
| Всего на ноде | 8 ядер | 32 ГБ |
| ОС ноды (system/kube-reserved) (5 %) | −0,4 | −1,6 ГБ |
| Демонсеты кластера (мониторинг/логи) | −0,5 | −1,5 ГБ |
| Порог вытеснения | - | −1 ГБ |
| **Доступно приложению** | **~7 ядер** | **~28 ГБ** |

#### Количество рабочих нод по ёмкости

- По CPU: 17 / 7 ~ 2,43 -> **3 ноды**
- По RAM: 30,25 / 28 ~ 1,08 -> **2 ноды**

Определяющим фактором при расчетах - `CPU`: **3 рабочие ноды**.

### Запас на отказ минимум одной ноды (N+1)

> Чтобы кластер пережил выход из строя **минимум одной** рабочей ноды,
мощность остальных нод должна покрывать пиковую нагрузку в период процедуры миграции на запасную:

- Необходимая полезная мощность(у же с вычетом для служб функционирования нод) на оставшихся нодах:
  - CPU: 17 ядер -> нужно 17 / 7 ~ 2,43 потребуется минимум **3** работающие ноды;
  - RAM: 30,25 ГБ -> нужно 30,25 / 28 ~ 1,08 потребуется минимум **2** работающие ноды.
- определяющий фактор - `CPU в непрерывной работе`, нужно **минимум 3 ноды**;
- добавляем 1 ноду про запас: **3 + 1 = 4 рабочие ноды**.

#### При отказе одной ноды (остаётся 3 ноды)

- CPU: 3 × 7 = 21 ядро доступно > 17 ядер необходимо
- RAM: 3 × 28 = 84 ГБ доступно > 30,25 ГБ необходимо

> **Промежуточный вывод: 4 рабочие ноды по 8 vCPU / 32 ГБ.**

### Control-plane ноды (для self-hosted Kubernetes)

> Так как Control-plane это отдельный тип нод, на них выполняются apiserver, etcd,
controller-manager, scheduler

> Поэтому требуемые ресурсные расходы дополняются.

```
Для отказоустойчивости и избежания split-brain при работе etcd-хранилища необходимо нечётное количество = 3 нодам.
```

> Рекомендуемые `параметры для control-plane` переводим в разряд `Необходимых` под малый/средний кластер:

**4 vCPU / 8 ГБ** на ноду в 3шт.:

| Параметр | Необходимо |
|---|---|
| Количество нод control-plane | 3 |
| vCPU на ноду | 4 |
| RAM на ноду | 8 ГБ |
| **Итого** | **12 vCPU / 24 ГБ** |

```
Если используется арендуемый Kubernetes (managed control plane,например в облаке),
то расходы на control-plane ложатся на провайдера,
и достаточно только рабочих нод.
```
